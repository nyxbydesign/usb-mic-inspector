# Android audio and USB routing investigation

Initial source investigation: 2026-11-11; descriptor compatibility update: 2026-11-14. Primary sources below describe Android/AOSP and upstream Linux, not a verified Pixel policy implementation. A subsequently supplied USB descriptor report is used for offline regression checks; it does not establish physical audio routing behavior.

## Public APIs do not establish a global mic-only override

`AudioRecord.setPreferredDevice` applies to that AudioRecord. A preference is not guaranteed to be the actual route. Query `getRoutedDevice` while recording, inspect read errors and capture silencing, and distinguish this app's result from another application's input. [AudioRouting reference](https://developer.android.com/reference/android/media/AudioRouting), [AudioRecord reference](https://developer.android.com/reference/android/media/AudioRecord).

`AudioManager.setCommunicationDevice` takes a sink/output device. Android chooses a matching source automatically. Concurrent requests prioritize the application controlling audio mode. Selecting the phone speaker therefore does not express the desired combination of phone mic and USB headphone output. [AudioManager reference](https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo)).

The USB automatic-routing setting is checked before `UsbAlsaDevice.start()`, which starts input and output. It is not a public input-only exclusion list and may be applied at connection time. This project does not change it. [Android 16 UsbAlsaManager](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/services/usb/java/com/android/server/usb/UsbAlsaManager.java), [UsbAlsaDevice](https://android.googlesource.com/platform/frameworks/base/+/master/services/usb/java/com/android/server/usb/UsbAlsaDevice.java).

## ADB/LADB/Shizuku: distinguish app privileges from shell privileges

`MODIFY_AUDIO_ROUTING` has protection level `signature|privileged|role` in AOSP Android 16. It is not an ordinary runtime permission that an APK can acquire through `pm grant`. Granting `WRITE_SECURE_SETTINGS` or using reflection does not itself grant audio-routing authority. [Framework permission declaration](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/core/res/AndroidManifest.xml).

**There is a relevant shell exception:** AOSP Android 16's `com.android.shell` manifest declares `MODIFY_AUDIO_ROUTING` for system media-router testing. Thus a blanket claim that ADB/shell can never call privileged audio-routing services would be too strong. This does not confer the permission on an ordinary app or prove that an OEM image, LADB session, or Shizuku-mediated call has it. [Shell manifest](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/packages/Shell/AndroidManifest.xml).

`AudioService.setWiredDeviceConnectionState(AudioDeviceAttributes, int, String)` enforces this permission, and attributes carry an input/output role and address. A properly authorized shell process might mark only the actual USB input disconnected while leaving its output connected. That would affect Android policy more directly than stealing a USB interface. This is a **candidate for device-specific investigation**, not an implemented or tested solution. The hidden API signature, caller identity, granted permission, exact address/type, framework inventory, Audio HAL behavior, restoration and reconnect handling all need verification first. Do not use guessed Binder transaction numbers. [AudioService](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/services/core/java/com/android/server/audio/AudioService.java), [AudioDeviceAttributes](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/media/java/android/media/AudioDeviceAttributes.java), [IAudioService](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android16-release/media/java/android/media/IAudioService.aidl).

The read-only helper in `shell-helper/` checks this capability without changing policy. A shell permission denial is a blocker, not a reason to alter security settings. No permissions, SELinux rules, hidden-API exemption settings, boot state or credentials are changed by this project. Root-only audio policy edits, sysfs unbinding and custom ROM changes fall outside scope.

## USB forced capture claim

`claimInterface(intf, true)` requests exclusive access and may disconnect the kernel driver. `releaseInterface` releases the claim; the API does not promise reconstruction of the original ALSA/framework routing state. [UsbDeviceConnection reference](https://developer.android.com/reference/android/hardware/usb/UsbDeviceConnection).

Endpoint IN means device-to-host, so an audio isochronous **data** IN endpoint can represent capture. A feedback IN endpoint can belong to playback and must not be treated as capture. Interface numbers, all alternate settings, class/protocol, AC collection membership and terminal links matter; array indexes or direction alone are insufficient. The gate supports only a conservative UAC1 subset; rejection does not mean the DAC is defective. [USB Audio 1.0 specification](https://www.usb.org/sites/default/files/audio10.pdf), [USB host overview](https://developer.android.com/develop/connectivity/usb/host).

The initial parser rejected every additional interface class, including a separate HID interface. Version 0.2 explicitly models one narrow non-boot HID layout alongside the supported audio interfaces. HID descriptors and interrupt endpoints are validated separately and must not share an interface number, endpoint address or AudioControl collection membership with the audio streams. The app never claims or communicates with that HID interface. An interrupt IN endpoint on HID is not microphone capture. Supporting the composite descriptor layout only establishes which capture interface may be offered for a manual experiment. [USB HID 1.11 specification, sections 6 and 7](https://www.usb.org/sites/default/files/hid1_11.pdf).

In upstream Linux v6.1 `sound/usb/card.c`, normally parsed streaming interfaces are claimed with the `USB_AUDIO_IFACE_UNUSED` marker. The disconnect callback returns early for such an interface, whereas a primary/control interface disconnect shuts down the card. This distinction makes a strictly separate capture-interface experiment technically conceivable. It **does not remove the input from Android audio policy** and does not establish fallback, working playback or restoration on a Pixel. Shared state, vendor changes and stale framework registration remain unresolved. [Linux v6.1 card.c](https://raw.githubusercontent.com/torvalds/linux/v6.1/sound/usb/card.c).

Even a successful claim could leave Android selecting the phantom input and recording silence or returning an error. Success requires actual device testing, with continuing USB playback and independent target-app microphone evidence. An AudioRecord result inside this app cannot satisfy Discord or telephony acceptance.
